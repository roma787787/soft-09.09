# Bridge Liquidity Tracker

Telegram-бот, который по тикеру показывает, сколько токена лежит в
контрактах-хранилищах мостов по всем сетям. Задача — до отправки средств
понять, хватит ли на стороне назначения ликвидности на вывод: если её
мало, токены зависнут в мосте.

Поддерживаемые мосты:

| Мост | Как находится контракт-хранилище |
|---|---|
| **Wormhole / Portal** | Token Bridge — один фиксированный контракт на сеть, держит все залоченные в нём токены. Адреса берутся из официального реестра Wormhole (`@wormhole-foundation/sdk-base`) и сопоставляются с нашими сетями по chain id, а не по названию |
| **Hyperlane** | Warp Route: публичный реестр маршрутов, читается из пакета `@hyperlane-xyz/registry`. Обновляется вместе с зависимостью |
| **LayerZero (OFT)** | Четыре источника подряд: публичный реестр OFT (`metadata.layerzero-api.com`), опрос самого контракта токена и обход сети пиров — и то и другое для V2 и V1. Ручной конфиг `config/layerzero-lockboxes.json` — переопределение для того, чего не нашлось |
| **Stargate** | Пулы Stargate — это тоже LayerZero, но реестра по тикерам у него нет. Адреса генерируются из деплоев Stargate (`npm run sync:stargate`); учитываются только `StargatePool*`, которые держат залог, включая нативные пулы |
| **Across** | SpokePool — одно общее хранилище на сеть, как у Wormhole. Адреса генерируются из публикуемых Across деплоев (`npm run sync:across`) |
| **CCIP / Transporter** | Пул на токен, но искать его в списках не нужно: Router → OffRamps → OnRamp → TokenAdminRegistry → `getPool(токен)`. Всё спрашивается у самих контрактов |

Важно понимать, почему источники разные. CoinMarketCap отдаёт только адрес
самого токена в каждой сети, а не адрес хранилища моста. Токен о мостах
ничего не знает, поэтому адреса хранилищ приходится брать отдельно, и
у каждого протокола свой способ.

Дополнительно бот умеет определять протокол по адресу контракта и следить
за событиями контрактов в реальном времени — это осталось от первой версии
и работает параллельно.

## Быстрый старт

```bash
npm install
cp .env.example .env
# впишите TELEGRAM_BOT_TOKEN (получить у @BotFather) и, по желанию, свои RPC
npm run dev      # разработка (tsx watch)
# либо
npm run build && npm start   # прод-сборка
```

### Проверки (сеть не нужна)

```bash
npm run check:addresses   # длина и контрольная сумма EIP-55 всех адресов из справочника
npm run selftest          # арифметика диапазона блоков, разбор команд, декодирование событий, рендер карточки
npm run typecheck
```

```bash
npm run sync:across       # обновить адреса Across из публикуемых деплоев (нужна сеть)
npm run sync:stargate     # то же для пулов Stargate
npm run sync:svm          # список сетей на VM Solana из реестра Hyperlane
npm run sync:cosmos       # то же для сетей Cosmos
```

`check:addresses` стоит запускать после любой правки справочника адресов:
потерянный при копировании символ превращает константу в адрес, который
просто никогда ни с чем не совпадёт, и детекция молча деградирует вместо
того, чтобы упасть с ошибкой.

Контрольная сумма пересчитывается из строчной формы адреса и сравнивается с
исходной. Это не придирка к стилю: `getAddress()` из viem возвращает адрес
со смешанным регистром как есть, не проверяя его, поэтому вызов в
`try/catch` одобрял вообще всё — два адреса в репозитории были записаны
неверно, а проверка показывала 28/28.

## Деплой на облачный хостинг

Боту нужен постоянно работающий процесс (long polling), публичный URL не
нужен. На любом хостинге с автосборкой из GitHub (Railway, Render,
Fly.io, обычный VPS) порядок один:

1. Подключить репозиторий и ветку. Сборка определяется автоматически:
   `npm install` → `npm run build` → `npm start`.
2. Задать переменную окружения `TELEGRAM_BOT_TOKEN`. Остальные
   переменные имеют рабочие значения по умолчанию.
3. Смонтировать постоянный диск (volume) в `/app/data`, иначе список
   отслеживаемых контрактов будет теряться при каждом передеплое.
   Альтернатива: задать `DB_PATH` в уже примонтированную директорию.
4. Тип сервиса выбирать «worker» / «background worker», а не «web
   service»: бот не слушает HTTP-порт, и хостинг с проверкой порта может
   посчитать его упавшим.

В логах после старта должно появиться `bot launched, long polling active`.

## Команды бота

- `/info <тикер>` — сколько токена лежит в хранилищах мостов по всем сетям.
  Пример: `/info ARB`. Мосты, для которых хранилище вообще не найдено, не
  показываются. А вот мост, чьё хранилище проверено и оказалось пустым,
  называется отдельной строкой «пусто» — для вопроса «дойдут ли деньги»
  это самый полезный ответ, и молчание в этом месте читалось бы как
  «не проверяли».
- `/info <тикер> <сеть>` — то же, но только по одной сети:
  `/info USDC base`. У широко разведённого токена контрактов больше, чем
  влезает в сообщение, и тогда часть сетей отбрасывается — а перед переводом
  вопрос обычно как раз про одну конкретную сеть.
- `/liquidity <тикер> [сеть]` — то же самое, явным именем команды.
- `/info <адрес> [сеть]` — определить протокол моста по адресу и показать
  конфигурацию: endpoint/mailbox/core-bridge, версию, владельца, список
  связанных сетей с адресами на другой стороне. Без указания сети бот
  проверит адрес на всех поддерживаемых сетях параллельно.
- `/sources` — наполнение реестров: сколько сетей, маршрутов и тикеров бот
  знает прямо сейчас.
- `/ccip <сеть>` — показать по шагам, как бот доходит до пулов CCIP в этой
  сети, и где цепочка обрывается.
- `/lzmesh <тикер>` — откуда взялось покрытие LayerZero по этому тикеру:
  реестр, опрос контракта, обход пиров.
- `/lzchains` — у каких сетей известен eid LayerZero и откуда он взялся.
- `/diag` — проверить связь с нодами всех сетей.
- `/track <адрес> [сеть]` — включить отслеживание событий этого контракта в
  реальном времени с оповещениями в текущий чат.
- `/untrack <адрес> [сеть]` — выключить отслеживание.
- `/list` — список того, что отслеживается в этом чате.

Поддерживаемые сети «из коробки»: 42 — Ethereum, Arbitrum, Optimism, Base,
Polygon, BNB Chain, Avalanche, Unichain, Ink, Linea, World Chain, Mode,
Berachain, Blast, Celo, Scroll, Mantle, Sonic, Gnosis, Sei, Taiko, Fraxtal,
Soneium, Zircuit, Swell, Lisk, BOB, Plume, Superseed, Katana, HyperEVM,
Monad, Plasma, X Layer, Metal, 0G, zkSync Era, Cronos zkEVM, Moonbeam,
Aurora, Ronin, Boba (список в `src/config/chains.ts`).

Плюс сети **Cosmos** — Celestia, Injective, Neutron, Osmosis, Stride, Terra
Classic, Cosmos Hub, Noble, Dymension, KYVE, MilkyWay. Там ничего выводить не нужно: маршрут это контракт с обычным адресом, а
залог — обычный банковский баланс, один GET по REST.

У маршрутов собственного модуля Hyperlane (Celestia, KYVE, MilkyWay) адреса
нет вовсе — только hex-идентификатор. Их залог лежит в модульном аккаунте,
и его адрес тоже не выводится: Cosmos перечисляет модульные аккаунты
стандартным эндпоинтом `auth`, то есть сеть называет адрес сама. Модуль
держит залог всех маршрутов сети в одном аккаунте, поэтому строка одна на
сеть и деном, а не на маршрут — показать один и тот же баланс по разу на
маршрут значило бы умножить его.

Плюс сети на **VM Solana** — Solana, Eclipse, SOON, Sonic SVM, svmBNB,
Solaxy, Nara. Они не EVM, поэтому живут в отдельной таблице и читаются
своим слоем. Сама таблица генерируется из реестра Hyperlane
(`npm run sync:svm`) — оттуда же, откуда берутся маршруты, поэтому сеть,
названная маршрутом, всегда в ней есть.

Сеть добавляется одной записью: таблицы Wormhole, Across и Stargate
ключуются по chain id, поэтому новая сеть подхватывает их адреса сама, без
единой новой строки с адресом.

### Почему Solana устроена иначе

На EVM контракт-хранилище держит токен сам, поэтому его адрес — это весь
ответ. На Solana программа не держит ничего: токены лежат в отдельном
аккаунте, чей адрес выводится из программы и минта и ни в каком реестре не
опубликован.

Обе деривации подтверждены на живой сети, а не взяты из документации:

- **Hyperlane** — PDA от `["hyperlane_token", "-", "escrow"]` под программой
  маршрута, залог лежит прямо в нём;
- **Wormhole** — PDA от `[минт]` под программой Token Bridge.

Признак «держит залог» на Sealevel тоже другой: поле
`collateralAddressOrDenom` заполнено и у синтетических маршрутов, которые
чеканят supply. Решает `standard` — иначе двадцать чеканящих маршрутов
попали бы в отчёт как пустые хранилища.

Все сети на VM Solana выводят адрес одинаково — у них общая виртуальная
машина и общая программа Hyperlane, — поэтому Eclipse, SOON и остальные
стоили строки в таблице и ни строчки новой логики.

Команда `/svm <тикер>` перебирает все варианты деривации по одной сети на
каждую и показывает, что ответила сеть — на случай, если Hyperlane их
изменит или на новой сети они окажутся другими.

Мосты делятся на два типа, и от этого зависит, как ищется хранилище.
**Общие хранилища** (Wormhole Token Bridge, Across SpokePool) держат в одном
контракте на сеть все токены сразу — такому мосту достаточно задать один
адрес на сеть, и дальше он отвечает по любому тикеру. **Контракт на токен**
(адаптеры LayerZero, warp-маршруты Hyperlane) требует реестра: если тикера в
нём нет, показать нечего.

Wormhole развёрнут не везде: у Linea, Mode и Blast нет контракта Token
Bridge. Раньше по ним приходили только строки Hyperlane — теперь эти три
сети закрывает Across.

Команда `/sources` показывает текущее наполнение всех реестров: сколько
сетей, маршрутов и тикеров бот знает прямо сейчас.

## Как собирается отчёт по ликвидности

1. Тикер уходит в CoinMarketCap (`/v2/cryptocurrency/info`), оттуда
   приходит адрес токена в каждой сети. Нужен ключ `CMC_API_KEY`; без него
   работает только поиск по адресу контракта.
2. Для каждой сети подбираются контракты-хранилища:
   - **Wormhole** — фиксированный Token Bridge этой сети. Таблица не пишется
     руками: она выводится из реестра Wormhole по chain id, поэтому новая
     сеть в `chains.ts` получает свой Token Bridge автоматически;
   - **Hyperlane** — маршруты из реестра, где тикер совпал, и у токена
     задан `collateralAddressOrDenom`. Синтетические маршруты пропускаются:
     они ничего не держат, а значит и о ликвидности не говорят;
   - **LayerZero** — реестр OFT по тикеру. Поле `type` решает всё: адаптер
     блокирует реальный токен и потому держит ликвидность, а обычный OFT
     чеканит и сжигает свой supply, у него хранилища нет вовсе. Что не
     нашлось в реестре, добирается опросом самих контрактов токена, а потом
     обходом сети пиров (см. ниже). Поверх всего действует ручной конфиг.
3. По каждому хранилищу читается `balanceOf` и `decimals` токена через RPC.
4. Сеть, чья нода не ответила, не роняет отчёт: её строки пропускаются, а в
   конце появляется предупреждение. Пустая строка никогда не должна читаться
   как «здесь нет ликвидности» — это противоположный по смыслу вывод.

### Тикер в реестре не всегда тот же

Мостовая версия токена часто живёт в реестре под собственным именем, а не под
именем оригинала: сегодняшний деплой USDT в LayerZero называется **USDT0**.
Поиск по точному совпадению тикера находил при этом устаревший адаптер с
парой десятков тысяч, а тот, где лежат настоящие деньги, оставался в соседнем
ключе.

Поэтому кроме точного тикера проверяются ключи «тикер плюс один-два символа».
Это способ **набрать кандидатов, а не сделать вывод**: каждый такой кандидат
обязан доказать через `token()`, что блокирует ровно тот контракт, который
CoinMarketCap указал для этой сети. Не доказал — не попал в отчёт, и в конце
написано, сколько адаптеров отсеялось.

### Сеть пиров LayerZero

Полного публичного реестра у LayerZero нет, и это главная дыра в покрытии.
Закрывает её то, что сами контракты знают друг о друге: у любого OFT есть
`peers(eid)` — адрес его же деплоя в другой сети, потому что именно так он
решает, чьим сообщениям доверять.

Поэтому одного найденного контракта — из реестра, из конфига или из опроса
адреса, который дал CoinMarketCap, — достаточно, чтобы развернуть весь
деплой: бот спрашивает у него пиров по всем подключённым сетям и по каждому
смотрит, адаптер это (блокирует ERC-20 — есть что мерить) или обычный OFT
(чеканит — мерить нечего). Так находятся сети, которых нет ни в одном
реестре и которых CoinMarketCap не показывает.

У найденного ERC-20 дополнительно сверяется `symbol()`: связь пиров
гарантирует, что контракты общаются между собой, но не что снизу лежит
именно тот токен, о котором спросили.

Практическое следствие: чтобы закрыть мост, которого нет в реестре,
достаточно добавить **один** его адрес в `config/layerzero-lockboxes.json` —
остальные сети бот доберёт сам. Посмотреть, что нашлось и откуда:
`/lzmesh <тикер>`.

Пулы Stargate закрыты отдельно и не требуют ручного ввода: их адреса
генерируются из деплоев самого Stargate. В таблицу попадают только
`StargatePool*` — они блокируют реальный залог. `StargateOFT*` чеканит
собственный supply и не держит ничего.

Нативные пулы держат монету сети, а не ERC-20, поэтому их баланс читается
через `getBalance`, и в отчёте такая строка подписана монетой сети: в отчёте
по WETH она покажет ETH, потому что выйдет из неё именно ETH. Пул попадает в
отчёт, только если нативная монета этой сети совпадает с запрошенным
тикером — контракт называется одинаково везде, но держит то, что зависит от
сети, а не от названия.

### Конфиг адаптеров LayerZero

Реестр LayerZero покрывает не всё, и иногда его нужно переопределить. Для
этого есть `config/layerzero-lockboxes.json`. Запись в нём имеет приоритет
над реестром для той же сети:

```json
{
  "ARB": {
    "ethereum": "0xАдресЛокбокса",
    "arbitrum": { "custody": "0xАдресЛокбокса", "token": "0xАдресТокена" }
  }
}
```

Короткая форма берёт адрес токена из ответа CoinMarketCap. Длинная нужна,
когда адаптер блокирует не тот контракт, который CMC указал для этой сети.
Файл перечитывается при изменении, перезапуск не нужен.

## Как устроено определение протокола

Определение построено в первую очередь на **прямых RPC-вызовах view-функций**
контракта (`endpoint()`, `mailbox()`, `wormhole()`, `typeAndVersion()`,
`localMessageTransmitter()` и т.д.), а не на слепом сравнении со списком
адресов — так бот распознаёт протокол даже если контракт не попал в наш
локальный справочник. Списки известных адресов (`src/protocols/addresses/*`)
используются как:

1. Дополнительное подтверждение уверенности результата (confidence: `high`
   вместо `medium`/`low`);
2. Источник адресов инфраструктуры моста на *других* сетях, чтобы можно было
   опросить peers/routers контракта.

EndpointV2 лежит по одному адресу почти везде из-за детерминированного
деплоя, но не на zk-сетях: они компилируют контракты иначе, детерминизм там
не держится, и эндпоинт стоит по своему адресу. Поэтому незнакомый адрес не
отбрасывается, а спрашивается: `eid()` отвечает только эндпоинт, и только у
V2 ответ лежит в диапазоне 30000–31000.

Важно: числовые идентификаторы сетей у каждого протокола (LayerZero `eid`,
Hyperlane `domain`, Wormhole `chainId`, CCTP `domain`) бот **не берёт слепо из
статической таблицы** — для каждой настроенной в `chains.ts` сети он сам
спрашивает у соответствующего инфраструктурного контракта её "родной" id
(`eid()` / `localDomain()` / `chainId()`) через RPC и кеширует результат на
час (`src/services/idMaps.ts`). Статические таблицы используются только как
подпись для сетей, к которым у бота нет RPC-подключения.

### Известные адреса — источники и актуальность

Адреса эндпоинтов/мейлбоксов/мостов в `src/protocols/addresses/*.ts` собраны
из официальной документации и реестров протоколов (LayerZero deployed
contracts, `hyperlane-xyz/hyperlane-registry`, Wormhole contract addresses,
Circle CCTP docs, Chainlink CCIP directory) по состоянию на **2026-09-09** и
прокомментированы источником в коде. Перед использованием в
продакшене/принятием решений на основе этих данных стоит свериться с
официальной документацией — адреса мостов меняются редко, но не никогда.

## Реальное время (`/track`)

Раз в `TRACK_POLL_INTERVAL_MS` (по умолчанию 60с) бот проходит по всем
отслеживаемым контрактам, группирует их по сети и делает `eth_getLogs` по
диапазону новых блоков **без фильтра по topics** — то есть ловит вообще любое
событие контракта, а не только те, чью сигнатуру мы явно знаем. Это осознанный
выбор: неправильно угаданный topic0 означал бы тихо пропущенные события.
Дальше `src/services/eventCatalog.ts` пытается красиво декодировать лог по
каталогу известных сигнатур (`OFTSent`, `SentTransferRemote`,
`DepositForBurn`, `TransferRedeemed` и т.д.); если не получилось — алерт всё
равно приходит, просто в сыром виде (номер блока, ссылка на транзакцию).

Ограничения по `TRACK_MAX_BLOCK_RANGE` и `TRACK_INITIAL_LOOKBACK_BLOCKS` в
`.env` бережно относятся к публичным RPC — для более частого опроса и
большего охвата используйте собственный RPC-ключ (Alchemy/Infura/QuickNode).

## Структура проекта

```
src/
  config/          сети (chains.ts) и переменные окружения (env.ts)
  protocols/
    types.ts        общие типы результата детекции
    layerzero.ts     детектор LayerZero
    hyperlane.ts     детектор Hyperlane
    portal.ts        детектор Portal / Wormhole Token Bridge
    transporter.ts   детектор Transporter (CCIP + CCTP)
    registry.ts      прогоняет все детекторы по адресу
    addresses/       справочники известных адресов + числовых id
  services/
    rpcClient.ts     кеш viem PublicClient по сетям
    idMaps.ts        динамическое разрешение eid/domain/chainId по живым RPC
    eventCatalog.ts  best-effort декодирование логов для алертов
    tracker.ts       поллинг eth_getLogs и рассылка алертов
    db.ts            SQLite-хранилище отслеживаемых контрактов
  bot/
    index.ts         сборка Telegraf-бота
    format.ts        рендер /info в HTML для Telegram
    parse.ts          разбор аргументов команд
    commands/        /info, /track, /untrack, /list, /help
  index.ts           точка входа
```

## Расширение

- **Новая сеть**: добавить запись в `src/config/chains.ts` (укажет viem
  `Chain`, env-переменную RPC и алиасы), при желании — адреса моста для этой
  сети в `protocols/addresses/*`.
- **Новый протокол**: добавить `protocols/<name>.ts` с функцией
  `detectXxx(client, chainKey, address): Promise<DetectionResult | undefined>`,
  подключить её в `protocols/registry.ts`.

## Известные ограничения

- Списки известных адресов покрывают не все 7 сетей для каждого протокола
  (например, не для всех сетей найден официально подтверждённый адрес Portal
  Token Bridge или CCIP Router) — детекция в таких случаях всё равно работает
  через ABI-пробинг, но с более низким уровнем confidence.
- LayerZero V1 и V2 поддержаны оба — и в отчёте по ликвидности, и в
  карточке по адресу. Разница только в том, какую функцию спрашивать:
  `peers(eid)` у V2 и `trustedRemoteLookup(chainId)` у V1. Номера сетей для
  V1 не зашиты — они выводятся из eid, которые бот читает у живых
  эндпоинтов (eid V2 = 30000 + номер V1). Связи видны только с сетями,
  подключёнными к боту: чужой номер сети спросить не у кого.
- Бот использует публичные бесплатные RPC по умолчанию — они могут быть
  медленными или ограничивать частоту запросов; для продакшена используйте
  собственные RPC-эндпоинты.
